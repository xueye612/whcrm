## 1. 执行摘要

当前仓库是一个单 Git 仓库，内部包含 Vue 2 前端、ThinkPHP 5 后端和部署 SQL。客户、联系人、线索、商机、合同、回款、发票、项目、任务、台账、收支、用户/角色/组织、消息、附件和日志等基础能力已经存在；未找到独立的奖励候选、季度绩效、质量门禁、多人贡献、项目知识库链接、商务费用合规审批或奖金发放模块。

“系统BUG/新增需求自动创建任务”已找到真实实现，主链路是：

`台账页面选择分类及项目/任务列表` → `ledger/save` 或 `ledger/update` → `Ledger::save/update()` → `maybeCreateProjectTask()` → `Task::createTask()` → 写入 `task`、`task_relation`、任务日志/消息/活动 → 回写 `customer_ledger.task_id/work_id/class_id` → 钉钉通知。任务完成/回退又可通过 `work/task/taskOver` 回写台账状态。

该链路必须保护，但在进入 P0 前必须先解决或确认四项基线风险：

1. **数据库基线不闭合**：代码读取和写入 `customer_ledger.work_id/class_id/task_id`，但仓库主 SQL 和现有增量 SQL均未定义这些字段。
2. **跨表写入无显式事务**：台账、任务、任务关系、日志、消息、活动和台账回写可能部分成功；当前仅以 `task_id` 非零做重复防护，并不能抵御并发重复创建。
3. **状态模型不足**：任务实质只有 `1进行中/2延期/5结束`，台账是六个自由字符串，项目只有启用/归档/删除语义；不存在目标 P0 的门禁状态机。
4. **制度原文缺失**：未在当前仓库、当前工作树集合及附件目录找到《山东文汇信息服务有限公司发展战略岗位绩效奖励制度及CRM改造方案.md》。本报告对六岗位与绩效的建议只能依据任务附件，不能替代制度第四章。

建议实施顺序为：先做数据库基线盘点和 P0 事务化闭环，再补项目实施、线索阶段、外包交付，最后统一奖励候选和季度绩效汇总。P5/P6 不应先于 P0–P4 的事实数据稳定。

### 4.1 核心真实关系

- 客户是 CRM 主体；联系人、商机、合同、回款、发票、台账和收支直接或间接引用 `customer_id`。
- 合同引用客户和商机；回款/回款计划引用合同；收支通过 `rel_type + customer_id/business_id/contract_id` 选择关联对象。
- 项目和任务对 CRM 对象的关系存为逗号拼接 ID：`work_relation`、`task_relation`。数据库未定义外键。
- 台账基线表有 `customer_id/business_id/contract_id`；当前代码还使用 `work_id/class_id/task_id`，但这些字段未出现在仓库 DDL/增量 SQL，属于必须先核实的环境漂移。

## 6. 当前状态机

### 6.1 任务

- 数据库：`crm_php-master/sql/crm180.sql:3367-3392`，`status tinyint NOT NULL DEFAULT 1`，注释为 `1正在进行、2延期、5结束`。
- 实际操作接口：`work/controller/Task.php:814-883` 只把任务切到 `1` 或 `5`；“延期”主要由截止时间计算筛选，并非受控跳转。
- 前端：任务以 `checked = status == 5` 表达完成/未完成，例如 `views/pm/task/index.vue:433-464`。
- 没有待评估、待内部验收、待发布、待客户验证、阻塞、暂缓、取消、重复、无需处理；没有 W/R/K 或评估完成门禁。

### 6.2 台账

- 前后端枚举一致：`待处理、处理中、待验证、待发布、已完成、已关闭`，证据为 `Ledger.php:100-106,200-206` 和 `views/crm/ledger/index.vue:597`。
- 数据库仅为 `varchar(20)`，没有字典表、CHECK 约束或状态历史表；历史 SQL 已有 `BUG/新需求/操作指导` 等旧分类：`crm180.sql:2787-2798`。
- 后端只验证目标值属于枚举，没有合法“从→到”跳转矩阵；任一有效状态可直接改为另一有效状态。
- “已关闭”要求关闭原因；“已完成”可记录完成回复：`Ledger.php:423-503`。
- “重复”只可能被当作关闭原因文本，不是结构化辅助状态。

### 6.3 项目

- `work.status` 是轻量生命周期字段，DDL 注释为 `1启用/0归档`，代码还使用 `2删除/3归档`：`crm180.sql:3423-3441`、`views/pm/project/index.vue:398`。
- 项目没有实施一级至四级/外包交付一级至四级、计划与实际里程碑、稳定期、验收结果、延期责任或奖金池状态。
- 项目任务列表“要做/在做/待定”是创建项目时生成的可编辑列表名：`work/model/Work.php:59-70`，不是受控状态机。

### 6.4 兼容判断

历史值是自由字符串和数字状态混合。P0 不应原地重新解释 `task.status=1/2/5`；建议保留旧值，新增版本化工作流状态及映射层，并把历史记录标记为 legacy。主要页面只展示中文名称，历史字母码仅保留内部兼容。

| 台账数据范围 | 登记人、处理人、客户团队、合同负责人/团队可见，管理员全量，`CustomerLedger.php:151-202` | 可复用，但台账 save/update 没有独立字段级权限 |
| 财务数据范围 | 依据管理员、负责人、团队 `finance_auth`，`FinanceRecord.php:443-621` | 可复用金额可见范围；不能替代费用审批/合规确认 |
| 字段权限 | 存在 `FieldGrant` 和 CRM 自定义字段唯一/授权体系 | 可用于 CRM 动态字段；P0 核心状态与金额规则不宜完全做成无类型自定义字段 |
| 审批 | 合同/回款/发票及 OA 审批已有 Examine 模型和页面 | 可复用审批引擎思想；需验证本人回避、多阶段固定职责和版本化审批快照 |
| 全局操作日志 | `RecordActionLog/SystemActionLog`，`admin_operation_log/system_log` | 部分更新会保存旧/新数据，但并非所有关键动作一致覆盖 |
| 业务日志 | `customer_ledger_record`、`work_task_log`、`crm_activity` | 可作时间线基础；缺结构化变更字段、规则版本和审核快照 |
| 通知 | 站内信、钉钉、企业微信、微信公众号 | 可复用适配器；建议事务提交后通过 outbox/队列发送 |
| 附件 | 统一文件上传下载及多业务关系表 | 可复用；需补文档类型、完整性状态、外链元数据和访问控制 |

## 8. 可复用能力与不可直接复用项

### 8.1 可复用

- 用户、部门、角色、菜单/按钮规则、项目成员角色。
- 客户、联系人、线索、商机、合同、回款、发票和团队关系。
- 项目、任务、标签、参与人、截止时间、附件、评论、任务消息。

- OA/CRM 审批模型（用于人工复核流程的基础）。
- 收支计划/流水、收入支出方向、支付方式、凭证、客户/商机/合同关联。
- 站内信、钉钉、企业微信、微信公众号通知。
- 操作日志、业务活动、附件上传、Excel 导入导出。

### 8.2 不能直接复用或只能部分复用

- `crm_achievement` 是销售目标，不是绩效评定或奖金候选。
- 任务 `status` 只有粗粒度完成态，不能塞入 P0 全流程而不破坏旧查询。
- `work_task_class` 是用户可编辑看板列，不能作为强约束业务状态。
- 台账状态是自由字符串且无跳转规则，不能承载上线门禁。
- `finance_record` 能记录收支，但没有预算审批、外部服务主体、协议/票据合规状态、奖励/商务费用分账和不可转换规则。
- `crm_activity`/文本日志没有稳定的事实类型、规则版本、金额计算快照和审核链。
- 逗号拼接 ID 的 `task_relation/work_relation` 不适合新增长期演化的多人贡献、里程碑和证据关系。
- 未找到飞书、知识库、接口文档、业务规则、开发变更、上线模块、使用指导的结构化链接字段。

## 9. 历史数据与迁移风险

1. **字段漂移**：生产库是否已有 `customer_ledger.work_id/class_id/task_id` 无法从仓库确认。开发前必须只读导出实际 `SHOW CREATE TABLE`/`information_schema` 快照并与仓库 DDL 对比。
2. **历史任务**：新增 W/R/K、验收、风险等字段必须允许 NULL；NULL 表示“历史未评估”，不能自动解释为最低/默认等级。
3. **状态兼容**：旧 `task.status=1/2/5` 和台账历史文本需保留映射，不应批量覆盖。新工作流应带 `workflow_version`。
4. **关联完整性**：数据库没有外键，台账 `task_id` 也缺仓库 DDL；需要审计孤儿台账、孤儿任务、重复任务、错误 work/class 组合。
5. **去重**：线索/客户/联系人页面有唯一性校验入口（如 `views/crm/leads/Create.vue:227-228`、`customer/Create.vue:287-288`），动态字段有 `is_unique`；主表未见名称/手机号数据库唯一索引。现状是应用层可配置校验，不是统一标准主体查重。
6. **软删除不一致**：任务用 `ishidden/is_archive`，项目用 `ishidden/status`，CRM 模型保留 `is_deleted/delete_time` 字段；迁移查询必须按各模块语义过滤。
7. **无外键**：迁移需显式做引用完整性检查，不能依赖数据库拒绝脏关系。
8. **字符集/快照质量**：`crm180.sql` 的部分中文注释乱码且包含样例数据；不能直接作为可靠生产迁移包。
9. **回滚能力**：现有增量 SQL 有个别幂等检查，但未找到统一迁移账本、down 脚本或自动回滚。建议采用“先加后切、可重复执行、反向兼容、备份验证”的 expand/contract 策略。
10. **收入与直接成本**：`finance_record` 可按合同/商机/客户记录 income/expense 和金额，能作为候选来源；但没有“实际到账软件及服务收入”“外包直接成本”“成本归属确认”的强类型字段，不能直接可靠计算奖金池。
11. **费用申请/外部服务方**：有计划、流水、凭证和合同/发票模块；未找到预算审批、报销/付款申请、外部服务主体、协议状态、合规确认的完整闭环。

建议迁移必须先做备份演练、预检、行数/金额校验和可重复执行验证；本轮未执行任何迁移。

## 15. 专项落地建议

### 15.1 项目知识库、飞书文档和 CRM 链接

现状未找到飞书/知识库/接口文档/业务规则/开发变更/上线模块的专属字段。建议仅在 CRM 保存 `link_type、title、url、owner_user_id、updated_at、completeness_status、version/ref`，不复制整份文档；URL 需域名白名单、访问权限提示和失效检查。项目详情按“目录、接口、业务规则、开发变更、上线模块、使用指导”六类展示。

### 15.2 自主签单医院 5% 综合池分账

现有收支记录可表达 income/expense、金额、合同和凭证，但不能保证“实际到账软件及服务收入”口径，也没有员工奖励与合规商务费用的强隔离。

建议建立同一业务来源下的两个独立子账：

- 内部业务获取奖励：上限 2%，进入 `reward_candidate`，只生成建议并人工审核。
- 合规商务拓展费用：上限 3%，进入独立费用申请/实际发生表，必须有预算、事项、审批、外部服务主体、协议/凭据和合规确认。

两者均引用同一到账事实，但类型、权限、审批、科目和结算完全分离；未发生费用不可转为奖金。系统不得提供向医院工作人员、采购或决策人员支付私人介绍费、回扣、购物卡或私人转账的对象类型或支付路径。

### 15.3 全员测试、质量评价、上线门禁与绩效联动

- 每个正式发布任务至少记录开发自测、一名非开发人员业务测试和必要复测；证据包括执行人、时间、环境、结果、缺陷链接和复测结果。
- 发布动作由后端门禁检查，不以页面勾选代替。
- 研发负责人对除本人外每人提交“完成良好/基本完成/需要改进”及证据；本人由总经理兼产品负责人和技术与项目负责人共同评价。
- 质量意见以 20%参考事实进入季度汇总并限制优秀，但最终评级仍人工确认。
- 严重失职进入独立责任认定，不通过自动扣款实现。

### 15.4 技术与项目负责人承接优化需求

台账保留“客户优化/产品改进→分类→评估→版本→任务→测试→发布→客户验证”的唯一链路。技术与项目负责人负责分类、W/R/K 初评、依赖/专业确认、版本归属和验收安排；所有字段变更进入结构化状态历史。现有自动建任务逻辑应被包进该服务，而不是绕过或另建一条重复入口。

### 15.5 六岗位简化考核重点

因制度原文缺失，下表仅为依据任务附件的**待产品确认建议**：

| 岗位 | CRM 自动汇总重点 |
|---|---|
| 总经理 | 经营结果、产品方向、重点客户/渠道、重大风险、授权与最终确认；不按普通任务数 |
| 研发负责人 | 技术交付、开发/数据/接口/打印、缺陷与复测、发布质量、稳定期修正、全员质量评价 |
| 技术与项目负责人 | 需求分类与评估、项目计划、风险依赖、客户优化、里程碑、验收、版本和知识完整性 |
| 客户成功工程师 | 客户台账、现场实施、培训/验收、线索核实、真实反馈、客户影响 |
| 驻场服务专员 | 现场人日、运维响应、问题复现、测试协作、文档和交接 |
| 市场运营专员 | 原始数据批次、统一查重、渠道/医院/外包机会、跟进完整性、归类和负责人建议 |

统一季度结构：核心职责40%、重点任务/项目30%、测试与质量20%、协作及 CRM/飞书记录10%；系统自动汇总事实，不要求额外日报/工时/复杂评分表，最终只人工确认优秀1.2、合格1.0、待改进0.6。

### 15.6 岗位协作、全员线索、行政轮值和简化评审

- 复用任务主负责人/参与人和项目角色，新增“贡献角色+时间段+证据”，避免把多人贡献压成一个负责人。
- 所有人可提交原始线索；市场运营专员统一查重、归类并建议当前跟进人，转移保留历史。
- 复用任务记录行政轮值、宣讲、汇报、检查和会议调度；使用任务类型/模板，不单建复杂行政系统。
- 审核采用“项目负责人初评→管理复核→总经理确认”，评审人集合在创建时固化；本人自动排除。总经理季度绩效由其他管理人员提出评价并保留签名/时间。

## 18. 调查结论
